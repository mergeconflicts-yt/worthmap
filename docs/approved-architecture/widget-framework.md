# Phase 1 in-app widget framework

Version 1.4 · 16 October 2026 · ARCH-FINAL-001 technical baseline.

Widget specification W1–W13 owns behaviour, the catalogue and layout as data. SYSTEM_DESIGN owns execution; DATABASE_DESIGN 5.1 owns persistence. This contract starts in v1 Phase 1. Later phases add widget modules through the same framework; they do not replace fixed screen cards later.

## 1 Ownership and interfaces

| OWNER | CONTRACT |
|---|---|
| `lib/app/widgets/` | Compile the widget/tile registry, validate descriptors, compose the generic surface host, coordinate activation and the editor. No financial formula or styling. |
| `lib/features/<area>/widgets/<key>/` | One independent module, builder and tests per catalogue key. Local presentation state belongs to this placement. It composes design components only. |
| `lib/design/` | `WidgetSlot`, `WidgetSection`, `WidgetEditBar`, `AddWidgetSheet`, `TileListSheet`, accessible reorder controls, neutral failure presentation and chart geometry. |
| Central read store | Canonical shared metrics and bounded list/chart/availability read models. One computation per compatible metric identity; immutable results and exact state metadata. |
| `lib/data/repositories/` | One layout repository and single-owner preference commands; no per-widget database queries. |
| Screen | Supply surface ID, fixed hero and template context. Build the generic host. No widget-key switches, concrete widget imports or per-card loading joins. |

The compiled `WidgetDescriptor` contains a stable key, widget/tile kind, l10n name, own surface, movement policy, allowed sizes (`full`, `half`), library-only status, release/feature gates, data-request policy, period policy, destinations, empty/hidden behaviour, a module builder and a pure preview builder. The preview builder accepts an immutable resident read model and presentation policy; it has no controller, repository or request capability. The registry is distinct from the domain metric registry. Default positions and sizes are not in descriptors; they come from the default layout file. Layout rows store item keys, section keys, order and sizes only; they never supply executable code, formulas, titles, metric values or arbitrary request parameters.

**Default layout file.** One declarative data file ships inside each release. It has a format version, `layout_version`, `catalogue_version`, and all ten surfaces: ordered sections (stable key, l10n title key or none) with ordered placements (item key, size), including the tile list. A closed add block has two parts (SY4-6):

- `add.widgets`: one entry for every addable key, including library-only and movable keys: add size and introduced layout version (`since`).
- `add.targets`: one entry per surface: a default target (section key, ordered anchor keys) and optional per-key targets.

Add resolves the target on the candidate: insert after the first anchor that is present; with no anchor present, at the end of the target section; with the target section absent from a customised surface, append that known file section. The registry supplies allowed sizes only. Registry size order has no meaning. Default placement size and add size may differ, but both must be allowed. A catalogue rename list is separate from the database schema version. It holds keys only: no amounts, text or personal data. The registry validates it at build time: every key exists, each size is allowed, no key appears twice on a surface, section keys are unique identifiers, at most 16 sections and 256 placements per surface, gates are declared and "Moves = No" widgets stay on their own surfaces. Validate the complete ten-surface set, reserved untitled/full-only tile layout, l10n title references, library coverage, add sizes, insertion anchors/fallbacks and introduced versions (1 through installed layout version). Reject duplicate/cyclic rename entries and collisions within each mapped layout. Renames are cumulative, flattened historical-key → current-key aliases. A changed rename map requires an increased `catalogue_version`, independently of `layout_version`. Several historical keys may name the same current key; this alone is not a collision. Retain every previous alias whose target still resolves in the current catalogue, so skipped releases and old recovery snapshots remain readable. Enforce 1 MiB on source bytes before UTF-8/JSON decoding, reject duplicate JSON object keys, then enforce 1 MiB canonical bundle bytes and 64 KiB canonical bytes per default surface. Both catalogue and layout versions are exact positive signed-64-bit integers (not booleans); introduced `since` values are exact integers from 1 through the layout version. Title-map keys are identifiers of 1–64 characters, with reserved `untitled` case variants rejected; titles must resolve to l10n. Reject unknown format versions. The test catalogue and default-file fixtures remain separate from production definitions. A malformed release file fails the build (W-L); runtime integrity failure still has the fail-closed path below. The file arrives only with an app release. No network path, download or remote configuration may supply or change a layout, a widget or a screen structure.

The implementation must supply `dart run tool/check_widget_layouts.dart` as a required build/CI gate before packaging; that tool is not implemented in this documentation repository. The layout is a compiled constant inside the read-only app bundle. Parse and validate it once, at build time, into one immutable typed bundle shared by resolver, editor and writer. Never load a bundle from an import, writable directory, shared file or recovery snapshot. A test asserts that the layout loader has no file-path, URL or byte-input parameter. Snapshots contain layout preference rows only. There is no runtime mutation or hot swap. A version/content change creates a fresh owner/session context; the writer also checks the frozen bundle digest. A runtime integrity/codec failure makes configurable layout unavailable without writing or substituting partial defaults; fixed heroes and navigation remain independent.

Registry validation also checks unique keys, valid surfaces, valid destinations, declared gates, complete defaults and namespace compatibility. Tiles belong only to `tiles:quickLook`. `wealth.ownOwe` and `investments.holdings` stay on their own surfaces. Enforce movement in the library resolver and again at the command boundary; a crafted request cannot bypass it. Library insertion is deterministic and comes only from `add.targets`. A build rejects a surface without a default target, a target section that the surface file does not have, or an anchor that is not a catalogue key. There is no section-picker flow; after Add, the person can move the widget with the section controls.

All nine SPEC W2 surfaces are registered from the framework's first build; each draws its fixed hero, then its layout. Feature gates determine which routes and modules are available. First-run, hidden amounts, first days and offline prices are state variants, not new preference surfaces. The same principle applies to Add expense, Inbox and account/allocation variants: a screenshot ID does not create a layout or a metric copy. State changes do not write layout rows. The fixed hero never enters a layout list. The SPEC catalogue remains the product source; code descriptors and l10n must be checked against it.

## 2 Independent placements and shared data

A placement is identified by (`hostSurfaceKey`, `itemKey`). Quick look child identity also includes its parent placement. Reordering, moving between sections, and half/full visual reflow keep these stable identities and local control state. The surface owns a placement-controller/lease map keyed by this identity; a section subtree or row index cannot own that lifetime. A keyed child alone is insufficient if reparenting disposes its parent scope. Bind each rebuilt view to the surviving controller and test focus restoration and control state during cross-section moves. Section host identity is (`surfaceKey`, `rawSectionKey`); an absent title never substitutes `untitled` for that key. Two placements have separate controllers, focus and geometry, but request the same canonical metrics when their financial meaning is the same. A placement ID must not enter a metric key.

A widget cannot import another widget's module/controller/state. Its data comes through the shared read store, including typed list/chart results and recorded-kind availability. It performs no SQL, aggregation, currency conversion, return calculation or local freshness timer. A list/chart requirement extends the shared bounded read-model contract; it is not permission for a private widget repository query.

A movable widget keeps its own SPEC-defined words, period, data scope and destination on every host. A host hero's filter, account selection or period cannot silently enter the widget's request. The descriptor names the governing SPEC rule. If the product has not defined a period policy, register it as unavailable for production until that rule is resolved; do not infer policy from an October sample or add a new selector. Display strings such as the calendar month come from the injected shared calendar context.

Independence applies to module state and layout actions. It does not prevent a confirmed financial change, global currency, hide-amounts mode, lock or shared metric failure from reaching every relevant consumer. Moving one card cannot reset siblings or alter their numbers. Two consumers of the same Missing metric both display Missing; neither fabricates an independent value.

## 3 Activation and bounded work

Resolve saved layout (or the installed default file when none is saved) → supported catalogue keys → release/feature/platform/movement eligibility → known empty-state policy → active placements, one level per section. Rendering never rewrites the raw layout. Metadata can retain an unrecognised or unreleased item or section key without constructing its module.

The host has two levels: surface host → `WidgetSection` hosts (title from the section key's l10n string, or none) → placements. Build it as **one flat virtualised keyed list**: section headers keyed (`surfaceKey`, `rawSectionKey`) and placements keyed (`surfaceKey`, `itemKey`) are siblings. A pair row is a layout of two sibling children, not a parent element. Placement controllers and leases live in the surface's placement map, outside the element tree, so a section move or row reflow re-attaches the same controller.

- **Section classes.** *Known:* `untitled` or a section of this surface in the installed file. *Retained:* a stored section that the installed file no longer has. A retained section keeps its raw key, draws with no title at rest, and its eligible children can move and hide. Its dormant children keep their slots.
- **Drawing.** At rest, a section with no active placement is not drawn. In edit mode, every stored section and every known file section of the surface is drawn, also when empty, so that it can receive a moved widget.
- **Stored size not allowed.** A stored size that this release no longer allows renders at the nearest allowed size (`half` → `full`, `full` → `half`). The row keeps its stored size; an unrelated Done keeps it. The widget stays movable and hideable. A build check blocks removal of an allowed size without a reviewed layout migration.
- **Effective width.** Pairing is inside one section, on the resolved visible order, greedy from the top: a `half` placement shares a row with the next visible placement if that one is also `half`; else it takes its row alone. The layout template sets the effective width from the window size class and the text scale: in the compact class, pairs stack when text scale exceeds the DESIGN threshold. A width or partner change never changes local state, focus, leases, canonical requests or numbers.

Placement identity stays (`hostSurfaceKey`, `itemKey`); the section is layout metadata, not identity.

Each placement has an activation lease. Acquire only when its route/surface is active, its layout includes the key and its gates permit it. An explicit hide, removal, gate change, route deactivation or lock first revokes admission, then releases subscriptions, callbacks, timers, animation controllers, chart geometry and child leases. Late callbacks check lease and database epoch before changing state or requesting work. Reorder, a section move and a widget move between sections do not revoke surviving leases.

No hidden module is built just to test whether it has data. The central store supplies bounded availability metadata for recorded-kind and catalogue empty policies, updated by source changes. It distinguishes known absence from a failed/unknown availability read. Known absence can suppress a slot where W11/W12 says so; an unknown read uses the defined Loading/Missing/Not available presentation. An accepted record can make an eligible slot appear automatically, with no refresh or hidden polling.

Shared requests are reference-counted by canonical key. Hiding one placement releases only its reference; another placement or fixed hero can keep the request alive. The last consumer can release consumer-only work. Writer-owned validation, source invalidation and required small-summary maintenance continue independently of widget visibility. The central calendar supplies time boundaries; do not create a timer per card.

`home.quickLook` composes a generic child host for the single `tiles:quickLook` preference. Tiles have independent modules and failure states. The parent reads shared eligibility metadata, never tile controller state. Parent removal releases all its child leases; a second visible parent placement keeps its own leases. All tiles known absent or layout-hidden suppress the parent. A tile failure must not masquerade as "no recorded tile" or hide siblings.

Off-viewport active-route content follows the existing bounded list/geometry policy. It is not permission to keep hidden or inactive-route modules alive. Release a scrolled-out module when the virtualised host unmounts it. Metadata and scroll position do not retain financial subscriptions.

### 3.1 Add widget previews

The shared store exposes a distinct `observeResident(requestKey)` capability: a cache-only **peek**. It can observe only already resident immutable values, list/chart results and availability metadata. It never calls normal `acquire`, refreshes a stale value, starts SQL, calculates a metric, decodes a file, loads availability, schedules work, starts a timer or fetches a logo. A stale resident value shows with its normal stale/Est. state. A cache miss or eviction shows the **Not loaded yet** preview state: the widget name and the words "Not loaded yet", with no number, no chart, no zero and no sample money. It is not Missing and not None recorded. Notifications may update the preview only when another admitted consumer or the writer has already loaded/published the shared result. Preview subscriptions do not pin results or prevent normal eviction.

Use the pure preview builder through a capability that cannot reach normal module controllers. Apply release, platform, financial-definition and movement gates before constructing it; previews cannot expose an unreleased financial module. Format the same model with the current hide-amounts policy; on Home with amounts hidden every preview is masked, including its spoken label. Do not cache an unmasked rendered bitmap. An expanded preview uses the same observation, with no new data request. Quick look preview children use the same rule.

Virtualise the sheet: at most 12 mounted preview observations, including the single expanded preview, with at most two off-viewport prefetch rows. Preview geometry shares the existing 32 MiB result/geometry LRU; no separate cache, timer or animation loop. Scrolling out, closing, lock, background, epoch replacement or a gate change revokes observation and releases geometry. A late callback checks its preview lease and epoch. Lock masks immediately. Reopening starts with current policy and resident data only.

Preview contents are inert: nested chart, navigation and financial actions cannot fire. Only the preview expansion control and Add control respond. Accessibility: a preview is one image-like semantic group with one spoken label that states the name and the main visible values (masked when amounts are hidden); inner semantics are excluded.

Adding changes the private layout candidate; normal data activation starts only when the committed placement becomes active.

Acceptance instruments all query, calculation, file/decode and gateway entry points. Cold, warm, scroll and expansion cases must make zero preview-originated calls. Test live resident updates, eviction, unavailable data, lock, hidden semantics, epoch replacement and repeated open/close cycles.

## 4 Failure and privacy handling

Each slot presents its own Loading, Missing, None recorded, Estimated, Hidden-amounts and Not available states. The screen must not await all cards in one all-or-nothing future. Typed provider/model failures and guarded action callbacks resolve within their placement. Retrying a slot reacquires a shared read; it does not replay a financial command or invalidate unrelated metrics.

A factory try/catch is insufficient for descendant build, layout, paint or asynchronous failures. App startup owns one safe framework/error-dispatch policy. Do not set and restore global `ErrorWidget.builder` or `Flutter.onError` while individual slots mount. The framework build fallback performs minimal work in a design-system leaf; it contains no raw exception text. Local model/callback failures use the slot's normal typed fallback. No error handler prints diagnostics, amounts, names, payloads or private identifiers, including in debug. Only allowlisted event names and counts can be logged.

Phase 1 must inject faults in the descriptor factory, descendant build, layout, paint, provider future and action callback. Include section-title build faults, one half-slot layout/paint failure and a surface resolver failure. Keep the failed slot's placement footprint until the user changes the layout; a fault cannot silently remove/re-pair its neighbour. Verify unrelated slots, fixed hero, editor and navigation remain usable. A generic build fallback is not proof of layout/paint recovery; the chosen host/render containment must pass these tests on the pinned Flutter build before acceptance. Vault lock/corruption remains a global safety state, not a widget-specific failure.

Hide-amounts formatting and semantics apply to every placement, title, meta field, preview and chart label. Amounts use the SPEC mask; dates, counts and percentages retain their allowed form. In-app descriptors, values and private IDs never cross into OS widgets, shortcuts or intents. Native surfaces remain generic launch actions behind unlock.

## 5 Edit session

Both the end-of-screen action and Settings open the same editor service. Hide, reorder, add, section move, widget move between sections, tile changes, Default and Undo change a bounded private candidate only. A section moves as one, up or down. A widget can move to another section of the same surface. Sizes and section titles come from the file; the person does not change them in v1. Add resolves the file's `add.targets` entry and `add.widgets` size; later moves use the section controls.

**Button path across sections.** Move up on the first widget of a section moves it to the end of the previous drawn section; Move down on the last widget moves it to the start of the next one. At that boundary the spoken label is "Move to [section name]" (untitled or retained: "Move to section [n]"). Drag and these buttons use one operation.

**"New in this version".**

- The group exists only for a customised surface (a stored row). It lists every eligible addable key (`add.widgets`, including library-only and movable keys, after all gates) whose `since` is greater than the stored `base_layout_version` and which is not stored on the surface in any section.
- "Seen" means: a Done committed an edit session that included the surface. The editor stamps the installed `layout_version` as `base_layout_version` on every customised surface of the session at Done. If only the stamp changes, Done still writes it once (one preference write, one read revision).
- Cancel, rendering, opening Add widget and Undo write nothing. Default returns the surface to inheritance, which has no group.
- A stored base version greater than the installed version makes ordinary edits read-only; Default stays available.

Widget content is inert in edit mode. A candidate hide immediately revokes that placement's active lease; Cancel or Undo reacquires only the restored committed placement against current shared data, not an old captured value. Candidate additions use the resident-only preview capability until Done commits them. The committed database layout remains unchanged before Done. Drag and Move up/down use one operation; edit controls retain one row, accessibility and one-add-control rules.

One session owns the entire nested edit. Home Default resets `screen:home` and `tiles:quickLook` together. Tiles is opened through Home edit mode, either from Home or Settings. It edits the same global tile preference used by every Quick look copy; this contract adds no tile-editor entry on other hosts. Cancel discards all nested edits. Undo reverses one complete session action, including a two-surface Default. Done submits the touched-surface patch once; it does not write on each drag/toggle. The private candidate retains explicit default scopes, and Undo restores their prior set. Default can be followed by more edits: the final layout may be custom even though a reset occurred. Successful layout commits notify only affected layout consumers and advance the visible read revision once; the preference transaction creates no financial recalculation or history. A newly active placement can then request one coalesced calculation for an uncached/stale metric; a warm current key is reused without another calculation.

Edit sessions are temporary UI state, not financial drafts. Back/navigation away and process loss discard an unsubmitted candidate; they never auto-commit it. Lock/background cancels drag and suspends editor input and subscriptions. A bounded candidate may remain in app memory behind unlock; it contains only keys, sections, order and sizes. A changed owner instance, catalogue or conflicting surface invalidates it. Any database/install epoch change, including restore and Delete all, discards the candidate, Undo log, preview observations and transient placement state. After process loss, load the committed layout. Do not persist a second draft layout or replay an uncertain submission automatically.

## 6 Phase 1 delivery and acceptance

1. Establish the shared read-store interface: canonical identity, immutable value/state, publication revision, acquire/release, resident-only preview observation and availability metadata.
2. Build the registry, default layout file and its build-time validation, generic two-level host (`WidgetSection`, `WidgetSlot`, sizes), independent feature module boundary, layout repository, writer preference protocol and editor in Phase 1.
3. Register the approved first-run Home catalogue/defaults using the same host. Test-only widgets/tiles stay in tests or the debug gallery; they never enter a release layout or unlock later product features.
4. Add later financial modules only when their release and financial-definition gates pass. No fixed-card screen implementation or second framework is accepted in a later phase.

| SPEC CHECK | REQUIRED FRAMEWORK EVIDENCE |
|---|---|
| W-A | Reorder/hide/add one placement: unchanged sibling data, local state and metric identity; only intended layout changes |
| W-B | Independent typed states and all six injected failure paths, plus section-title build failure, one half failing layout inside a pair row and one surface resolver failure; no private diagnostic/semantic leak |
| W-C | Same movable widget on two different host periods: identical canonical requests, words, period and destinations |
| W-D | Hidden, gated, inactive and removed-parent placements have zero subscriptions/timers/animations/geometry; stale callbacks rejected. Add widget previews with empty and warm cache make zero query, worker, normal-lease and module-activation calls |
| W-E | Add a synthetic descriptor/catalogue/l10n/module without touching a screen or another widget; import-boundary check |
| W-F | Retained sections with editable known children, dormant keys, stored sizes no longer allowed, parent-omission rejection, one explicit-empty form, whole-session Cancel/Undo/Default/Done, incompatible catalogue, rename collision and lost reply |
| W-G | Keyboard, reader, button/drag parity, light/dark, text 1.0/2.0, hidden amounts and semantics |
| W-H | Home+tiles and all-surface reset atomic; only preference rows/read revision change; financial facts, audit and dependencies unchanged. Delete all discards every layout row and editor/preview state |
| W-I | A changed test default file changes an untouched surface; no screen-code change |
| W-J | Conditional upgrade fixture: custom layout unchanged after release; all eligible newly introduced keys listed; unrelated Done, stamp-only Done, Cancel, Undo and Default behave as defined. Restore cases: snapshot with older base, newer base (read-only), retained section and renamed key |
| W-K | Section/cross-section moves and half/full reflow preserve controller, focus and lease identity; two unknown section keys and a real `untitled` section never collide |
| W-L | Unknown key/format, disallowed placement/add size, duplicate key, missing gate/library entry/surface, invalid l10n/anchor/version/rename map and exceeded limits fail the build |

Section/half-width geometry follows the design template, including text scaling and window size class; feature modules do not test screen width. Only the reflow threshold stays open. The reference layout harness tests SQLite and the command model only. It does not implement Flutter, prove these UI tests or satisfy device gates.

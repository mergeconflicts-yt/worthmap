# Execution boundaries and recovery

Version 1.1 · 16 October 2026 · ARCH-FINAL-001 technical baseline.

This contract refines SYSTEM_DESIGN, DATABASE_DESIGN and the query contract. SPEC remains the authority for product meaning. These are implementation requirements. The SQLite checks and small owner models do not implement the app, a regex engine, native cancellation or phone durability.

## 1 Bounded projection validation and publication

The large-work path has three separate stages: write private pages, validate a frozen set, then publish its pointers. Full validation never runs in the final writer transaction.

1. The owner admits a coherent group of canonical keys before calculation. Initial final-publication bounds are **128 keys, 128 distinct dependency scopes, 512 row effects and 256 KiB of encoded metadata**, for the whole group. Count trigger effects, status changes, pointer writes, dirty acknowledgements, job completion and read revision. Bound each metadata descriptor as well. Aggregate scopes must have tested membership invalidation; they cannot hide omitted dependencies. If a group cannot fit, keep its dependent values Updating and use a separately reviewed aggregate/group-pointer strategy. Splitting a required coherent group into independently current subsets is prohibited.
2. Stage all outputs, dependency rows, exact input pins, occurrence snapshots and coverage metadata through the owner in bounded pages. Each message uses the SHARED_STATE attempt tuple. Existing parser/message and derived-byte limits still apply. No worker gets a write connection.
3. Drain accepted writes for that attempt, then freeze **every child family and the generation metadata**, including inserts, updates, deletes and input pins. The owner issues a staging version and keeps a closed admission state. No further chunk can mutate the set. A deliberate unfreeze or member replacement invalidates validation before any write; it requires a new attempt/version.
4. Validate complete input closure, source selection, ordering, exact values, extrema, counts, gap boundaries and metadata in resumable bounded pages. Release SQLite read snapshots between pages. The frozen set and retained inputs provide stability; no long read transaction is needed. Cancellation and foreground admission occur between pages. Counts and coverage must be verified, not trusted because a worker supplied them.
5. Only after all validation passes, the owner keeps an in-memory certificate bound to its own fresh instance identity, database epoch, job UUID, attempt nonce, complete generation/key group, staging version, validation/algorithm version, captured dependency set, evaluation cutoff and calendar/clock policy. The certificate is an owner capability, not a boolean supplied by a worker or restored job row. Its bounded descriptor uses canonical bytes and compares full identities, not a hash alone.
6. In one admitted final writer transaction, require that certificate; compare the bounded dependency set, policy, epoch, lease and time boundary; verify group membership, pointer preconditions and the current dirty envelopes. Publish all pointers, mark generations and job complete, acknowledge only covered dirty ranges and advance the read revision once. Pins were already staged and become reachable with the same pointer switch. No scan, copy, hash or validation of the full output/history/pin set occurs in this transaction. Existing pointer triggers also see only the admitted bounded dependency set.
7. Restart, resume, owner replacement, lock/cancellation, expiry, append, changed member or method invalidates the certificate. Restart may retain encrypted staged pages, but must establish a new attempt and freeze/validate them again. Persisted progress is not a certificate. A changed source or clock makes publication ineligible; it does not make old values current.

Ordinary edits retain their existing bounded atomic source-and-small-result path. This protocol does not postpone small validated totals or add copies of canonical values. SQL guards seal published data; only the owner protocol seals **staging** data. Tests must exercise the actual owner routing, not infer the freeze from an FK.

Acceptance: reject late output, metadata and pin mutations; changed dependencies/time; certificate reuse after restart, cancellation or generation reuse. Compare small and large staged histories with the same group: validation work grows in bounded pages, while final work stays within the fixed admission bounds. Report page latency, final transaction latency and foreground queue delay separately on devices.

## 2 Import preview and Inbox publication

File parsing writes private staged rows, source claims and progress. It does not change visible Inbox rows or counts. Failed parsing, changed mapping and preview Cancel preserve this boundary. A changed mapping starts a new immutable parse configuration and attempt; only unresolved private claims may be reassigned by the owner. Accepted/undone source identities never become new financial candidates by this path.

**Send to Inbox** is distinct from financial Confirm:

1. The explicit action creates a durable `local_jobs` entry with `kind=inboxPublication` and the existing typed `import_job_inputs` links to batch, configuration and source descriptor. The source bytes need not still exist if all required structured rows are complete. The owner freezes the complete preview selection/configuration and admits one active publication attempt per batch. Its batch/job identities are the retry identity. Do not serialize a million selected IDs into one message. The stable staged row order and frozen batch define the complete selection; exceptions require a bounded paged descriptor before admission.
2. Prepare candidate Inbox rows and validate dedupe/claim ownership in bounded pages. `import_batches.inbox_published` stays 0. Q13 extracts a bounded candidate page before joining visibility metadata; private rows and payloads never enter feature DTOs. All metadata belongs to the encrypted vault. Only unaccepted candidates contribute to the pending count.
3. Freeze the prepared batch and validate its full count/selection in bounded pages under the attempt fence. Prepare the exact new shared Inbox count from the current count baseline. The final writer transaction compares that baseline's revision, batch status/configuration, frozen attempt and completeness certificate. It sets `inbox_published=1`, completes the job and publishes the count with one `read_revision` and `inbox_revision` increment. No per-row update occurs here. If another decision changed the count baseline, recompute/rebase before commit; never overwrite a newer count. Publication does not create financial history or totals.
4. The publication marker is one-way for a batch. A lost response resolves the same batch/job; it never recreates candidates or adds the count twice. Cancellation before commit leaves the batch private. Cancellation after commit resolves as published; later withdrawal is a separate explicit action. Restart revalidates staged completeness before publication and cannot infer it from progress alone.
5. `db_state.inbox_revision` increments once for every transaction changing pending membership or visibility: publish, withdrawal, acceptance, deletion or a direct authorised candidate. Bind Inbox cursors to epoch and this revision. A stale cursor restarts, including when a previously private row sorts before its old position. Scan sparse candidate pages with cancellation/progress; a rejected full page is not an empty Inbox. Advance over consumed returned/rejected candidates only. A 101st unreturned eligible sentinel stays after the cursor and is reread next page; a 100-row display page cannot discard it. Counts come from the same eligible set, not COUNT over all preparatory rows.
6. Confirm rechecks publication, review status, claim ownership and selected row revisions inside the command writer transaction. The all-selected financial command bounds still apply to Confirm. **Send to Inbox has no new 5,000-row selection cap; it uses private paged preparation and a bounded marker publication.**
7. An explicit import withdrawal sets batch status to `discarded` and atomically publishes the exact count delta and revisions. Calculate the remaining eligible count in bounded pages first; compare the captured Inbox revision at commit. Q13 and Confirm immediately reject the batch. Keep `inbox_published=1` as evidence that publication occurred. Paginate payload cleanup later. Accepted financial records require the existing financial batch Undo command; withdrawal cannot delete them or imply they were never accepted.

Only `review` batches with the marker are visible. A batch reaches `done` only when no pending candidate remains. A directly enabled capture source can use its explicit source permission instead of a file-preview action; it still uses owner-checked, atomic visibility and count publication. An orphan candidate or a claim/staged-row mismatch fails closed. The existing source setup action is not permission to bypass later policy revocation (section 4).

Migration 004 preserves existing v3 Inbox visibility by marking batches with existing candidate rows published. The owner validates legacy claim/configuration consistency before serving them; unsupported legacy states stay recoverable, not silently confirmed. New batches default to private. The migration does not reparse, post money or create source-history duplicates.

Acceptance: multi-chunk parse failure/cancel/configuration change; partial candidate preparation; interrupted/lost-reply Send; concurrent acceptance/deletion; publication behind a cursor; withdrawal before Confirm; restart; million-row sparse private/public candidates. Observe either complete eligible publication or none, with exact shared counts. Reference checks cover SQL visibility and transaction rollback only; production count/attempt admission and phone work bounds still need tests.

### 2.1 Direct structured review

F12 applies a holdings observation from X45. F16 confirms payslip/statement-derived areas from X69 or a policy from X69b. These product paths use direct review, not Send to Inbox. Manual, voice and receipt forms likewise use their specified Save action. The Inbox publication prerequisite in section 2 applies only to the Inbox route.

1. Parse into private encrypted staging/drafts. Freeze the review selection, parser/configuration versions, structured input, target revisions, source identity and attachment references before the explicit confirmation is submitted. Keep the complete source-to-draft provenance while it is required for deduplication and review. Do not retain discarded raw source text merely to create provenance.
2. The direct command has its own operation ID and typed confirmation route. In the same writer transaction, validate the current source reservation and staged-row revision, supported parser/configuration, review/selection digest, target revisions, lifecycle capability and exact financial invariants. No Inbox publication bit is required for this route. A caller cannot label an unreviewed Inbox candidate as direct review to bypass its route: the owner binds the route at draft creation and freezes it with the operation.
3. Atomically commit all selected linked effects, source-event claims, ChangeLog, dependency/read revisions, receipt and draft retirement. Reuse matched salary/cash effects; a holdings observation never manufactures trades or cost. Publish authenticated attachment files under the file/lease protocol before linking them. Over-bound plans or incomplete required inputs remain recoverable drafts; no partial acceptance.
4. An identity already accepted through either route resolves its existing operation or enters explicit match/review. It cannot post again through the other route. Lost replies and unknown commit outcomes resolve the same receipt. Only a proven rollback permits editing/resubmission under the existing command rules.

Use the same 100,000-effect / 16 MiB prepared-command and cancellation bounds as financial Confirm (DATABASE_DESIGN 6), including all linked document effects; the 5,000-source-row selection bound applies to batch review. This does not impose an Inbox UI on a direct document flow. S03/S04 tests cross-route duplicates, stale review/configuration, observation apply, selected payslip areas, policy Save, attachment failure, disk-full, interruption and repeated taps. No new financial rule is defined here.

## 3 Bounded data-supplied patterns

User/imported `CategoryRule` and `ParserTemplate` patterns run through a pure BoundedPatternPort. Do not execute them with synchronous backtracking RegExp in the shared worker. A ten-millisecond scheduler quantum cannot preempt that call. Dart documents exponential and polynomial backtracking cases. `Dart RegExp`.

The admitted implementation is a non-backtracking engine with a versioned supported grammar and explicit work accounting. Initial admission bounds: 1 KiB UTF-8 pattern, 16 KiB target field, 2,048 compiled states, 100,000 compile steps, 1,000,000 match transitions, 128 rules and 4,000,000 transitions across all rules for one record. Account for repetition/Unicode expansion during compilation before allocating states. Check cancellation at most every 4,096 work steps and between rules; tune these limits through S04. A complete parser chunk also obeys the scheduler quantum and message bounds. Larger valid work must remain resumable within a separately admitted job, never block foreground work in one synchronous call.

Retain original pattern bytes and grammar, engine, Unicode, case, anchoring and capture-policy versions in immutable parser configuration. Do not silently rewrite a pattern, truncate a field or substitute a different dialect. Unsupported syntax, limits or exhausted work returns a typed unsupported/incomplete result for preview/review; it is not "no match", a default category or an accepted transaction. Fixed trusted parsers also require bounded inputs and adversarial work tests. `Future.timeout` alone does not cancel synchronous work. No package is selected by this document; the S04 implementation must prove these properties before data patterns run.

Acceptance includes nested repetition, overlapping alternatives, long almost-matches, counted expansion, Unicode expansion, many-rule totals and cancellation during compile/match. Preserve original input and partial drafts on a limit. Measure foreground admission while these cases run. The Python architecture tests do not prove this engine.

## 4 Capture policy and delayed callbacks

Each enabled source has a durable source identity and monotonically increasing policy/configuration revision. Each capture attempt also carries a fresh owner/runtime capability, installation epoch and database epoch. The planned source tables must store the revision with the versioned source configuration; this reference foundation does not yet implement those product tables. Do not put the policy in an untyped settings blob or reuse the database-wide epoch as a source revision.

Disable, permission withdrawal, mapping/account/configuration change, lock, restore and deletion revoke admission before waiting for native cancellation. Disable/re-enable increments the revision even if the final settings equal the original settings. A new attempt gets a fresh capability. The owner compares the complete tuple and current enabled/permission state in the same transaction as accepted staging and source-cursor advancement. Reject delayed records and cursor updates from an old attempt without changing either. Already accepted local drafts remain reviewable under their captured configuration; they do not confer authority to accept another callback.

Native work can finish after cancellation. Its result cannot bypass the owner or publish a temporary file without the existing lifecycle/file-lease checks. Tests cover off→on, A→B→A configuration, permission loss, lock, owner restart, restore, cursor races and callbacks delivered after native cancellation returns.

## 5 Explicit restore does not replay pending commands

Normal crash recovery within the same active generation remains receipt-first resolution of the original operation ID. **Explicit snapshot restore is different.** A snapshot can contain a submitted/running intent and frozen input but no receipt. Its old Save action is not authority to perform a new financial write after restore.

Before activating staged G+1, enumerate intents in bounded keyset pages and compare each with G+1's own receipts. Preserve committed receipts, original digests and their outcomes exactly. Reject inconsistent committed/missing-receipt states for recovery; never invent a receipt. Change every receipt-less submitted/running intent to `cancelled` with an incremented state version and a safe `restoredForReview` code. Preserve its only structured input until a supported new editable draft is durably created; unsupported input stays recoverable in a typed state. Create fresh draft handles and epoch bindings. Never queue these old operations automatically.

This classification occurs wholly in staging and is repeatable after interruption. After user confirmation, quiesce/drain old active writers, invalidate their capabilities and verify the staged preparation/identity before the pointer switch. A partial classification cannot become active. Rollback before switch keeps G intact. A later explicit review and Save creates a **new operation ID** and validates current data; an old receipt-less intent cannot be resubmitted. An existing receipt resolves its recorded outcome, never reruns it. Restore forces optional networking off independently of this rule.

Acceptance: snapshots before intent, after submitted/running intent and after receipt commit; interruption during classification and switch; no automatic posting, unchanged selected-snapshot totals, retained receipt/digest and recoverable input. SQLite backup/transaction checks are structural evidence only; DB-F must prove native file, key and process-kill behaviour.

## 6 Protected database identities

Reference schema version 4 adds before-insert and before-update conflict guards for 75 protected table families. Insert guards check the primary key and every independent UNIQUE key, including both sides of partial live predicates. Update guards reject primary-key changes and unique conflicts with another row. Thus INSERT/UPDATE replacement cannot silently delete retained identities, even when recursive triggers are disabled. Existing immutable-update, authored-delete and history-retention guards still apply.

The connection factory nevertheless must set **and verify** `recursive_triggers=ON` **on every open**, with the existing foreign-key/cipher/temp/durability settings. Ban both `INSERT OR REPLACE` and `UPDATE OR REPLACE`, including generated repository conflict strategies. Protected tables use an indexed lookup followed by explicit INSERT or supported UPDATE through the single writer. Their before-insert guards intentionally also reject existing-key `ON CONFLICT DO UPDATE/NOTHING` and `OR IGNORE`; do not use those forms to resolve identity. SQLite runs REPLACE as deletion/insertion rather than an ordinary update. `SQLite conflict handling`.

For protected integer primary keys, the production owner allocates explicit positive local IDs before binding. Do not use the undefined `BEFORE INSERT NEW.rowid` of an omitted key as a conflict identity. The structural test helpers still exercise SQLite allocation for ordinary new rows; that does not approve implicit production ID allocation. UUID/compound identities retain their existing codecs. IDs do not leave the device.

The intentionally mutable pointer/layout/cache/staging families outside these generic guards are `current_balance_anchors`, `current_quotes`, `current_occurrence_decisions`, `current_projections`, `layout_surfaces`, `layout_sections`, `layout_items`, `public_asset_cache`, `dirty_ranges`, `draft_payloads`, `draft_references`, `draft_attachments`, `transaction_candidate_keys` and `search_documents`; each retains its specific contract. The writer-wide replacement ban still applies. The three layout tables also have `layout_*_no_replace` triggers, so a conflicting INSERT or UPDATE (including OR REPLACE) aborts instead of cascading a delete (DB4-10). FTS internals remain engine-owned.

`db_state` cannot be deleted and re-created. Its epoch and counters belong to the lifetime of that vault. Delete all removes the whole vault under the native lifecycle protocol. Migration 004 adds these guards plus the Inbox fields, preserves financial rows/evidence, and has v1→v4, v2→v4 and v3→v4 parity and rollback checks. This is executable reference SQL, not a production Drift migration.

## 7 Saved close preparation and admission

F18 Save and finish is one authored command. A long history can produce many retained allocations and evidence links, even if its screen shows few numbers. The final projection-pointer protocol in section 1 does not by itself bound that copy. Current `close_*` rows are immutable, reachable evidence; they cannot be used as private staging.

1. Create the operation identity and disk-backed encrypted plan using the existing intent/payload-chunk protocol. In cancellable bounded pages, prepare and validate the entire close revision: exact values/states, coverage, cutoff, method versions, allocations, quote/detail/entity/attachment bridges, completion change, history, dependency/read revision and receipt. Retain source generations, files and key versions under leases until the outcome is known. No close row or completion flag changes during preparation.
2. Freeze the plan under fresh owner, installation/database epochs, attempt and staging version. Independently verify full counts, bytes and input closure before issuing an owner-held certificate. Capture a bounded dependency frontier using tested aggregate scopes (at most 128 scopes); every relevant source edit must invalidate it. A full source scan or hash cannot run in the final transaction. Re-prepare if the frontier or clock/cutoff policy changes.
3. Apply general prepared-command admission: **at most 100,000 logical row effects and 16 MiB encoded plan**, including all trigger, registry, audit, receipt and index-document effects. Reserve actual index/FTS page, WAL and rollback space separately. The 5,000-selected-source-row limit is additional for batch confirmation, not a limit on evidence rows in a close. Apply the native operation-scoped cancellation and 10-second execution deadline from DATABASE_DESIGN 6; expiry starts cancellation and is not proof of completed rollback.
4. In one transaction, check the certificate/frontier and insert the complete immutable close/evidence set, workflow completion, history, receipt and shared read revision. Consume the already validated bounded plan; do not recalculate, copy an unbounded live query or wait for external work while holding the writer. After commit, start the optional recovery snapshot as a separate job. Snapshot failure does not unclose the month.
5. Over the bound, leave the month open and all close rows unchanged; retain the review/input in a typed capacity state under the existing draft/intent rules. Do not drop evidence, weaken coverage, split one close into visible partial commits or change its requested period to fit. No successful receipt is written. An interruption/unknown commit resolves the original receipt before retry or edits; a proven rollback leaves the draft recoverable.

S03 and performance workload P22 must cover baseline, large and stress histories. Record evidence counts/bytes, preparation duration, final writer duration, cancellation resolution, WAL peak and foreground queue delay. If a required release workload exceeds admission, that workload is not supported by this schema. Before release it needs a reviewed migration for paged immutable close evidence with one bounded publication pointer; do not claim that extension exists today. This explicit capacity boundary protects retained evidence and the single writer.
